## PHASE 1 — Setup Backend Laravel (REST API + MySQL)

```
Buatkan project backend Laravel baru bernama "baloga-api" dengan struktur berikut:

TECH STACK:
- Laravel 11
- MySQL sebagai database
- Laravel Sanctum untuk autentikasi API (token-based, bukan session)
- Laravel Fortify untuk validasi login/register aman (rate limiting, hashing bcrypt)

DATABASE SCHEMA (buatkan migration untuk semua tabel ini):

1. users
   - id, name, email (unique), password (hashed), avatar_url, level, xp, points,
     species_found, badges_count, created_at, updated_at

2. species (master data monster/hewan/tumbuhan)
   - id, name, latin_name, category (enum: hewan/tumbuhan), rarity (enum: common/rare/epic/legendary),
     habitat, food, ecological_role, conservation_status, fun_fact, model_3d_url, thumbnail_url,
     base_cp, created_at, updated_at

3. game_locations (titik lokasi taman/area game, untuk validasi radius)
   - id, name, latitude, longitude, radius_meters, created_at, updated_at

4. spawn_points (titik dimana monster bisa muncul di map)
   - id, species_id (FK), latitude, longitude, active, respawn_minutes, created_at, updated_at

5. captures (log history capture per user)
   - id, user_id (FK), species_id (FK), captured_at, latitude, longitude, cp_result, created_at

6. inventories (monster yang dimiliki user)
   - id, user_id (FK), species_id (FK), quantity, first_captured_at, created_at, updated_at

7. items (Eko-Sphere, Eco Scanner, Nature Radar, Lucky Leaf)
   - id, name, description, icon_url, type (enum: capture_ball/scanner/radar/booster), created_at, updated_at

8. user_items (inventory item milik user)
   - id, user_id (FK), item_id (FK), quantity, created_at, updated_at

9. missions (daftar misi harian/mingguan)
   - id, title, description, type (enum: daily/weekly), target_count, xp_reward, icon_url,
     created_at, updated_at

10. user_missions (progress misi per user)
    - id, user_id (FK), mission_id (FK), current_progress, is_completed, reset_at, created_at, updated_at

11. badges
    - id, name, description, icon_url, requirement_type, requirement_value, created_at, updated_at

12. user_badges
    - id, user_id (FK), badge_id (FK), earned_at, created_at, updated_at

Buatkan juga Eloquent Model untuk semua tabel di atas lengkap dengan relationship (hasMany, belongsTo, dll)
sesuai foreign key yang disebutkan.

Setelah migration & model selesai, jalankan migrate dan tampilkan struktur akhir folder project.
```

## PHASE 2 — REST API Endpoints (dengan Security)

```
Buatkan REST API Controller & Route untuk backend Laravel "baloga-api" dengan ketentuan SECURITY berikut
WAJIB diterapkan di semua endpoint:

SECURITY REQUIREMENTS (wajib, karena app akan dipublish ke Play Store):
1. Semua endpoint (kecuali register/login) harus dilindungi middleware auth:sanctum
2. Semua input HARUS divalidasi pakai Laravel Form Request (jangan validasi inline di controller)
3. Terapkan rate limiting: 60 request/menit untuk endpoint umum, 5 request/menit untuk login/register
   (gunakan Laravel throttle middleware)
4. Password di-hash dengan bcrypt, JANGAN pernah kembalikan field password di response JSON
   (gunakan $hidden di Model)
5. Gunakan API Resource (Laravel Resource) untuk semua response, jangan return Model mentah,
   supaya tidak ada field sensitif yang bocor
6. Validasi koordinat GPS di server-side juga (jangan percaya validasi radius yang dilakukan di
   client Flutter, karena bisa dimanipulasi/fake GPS) — tolak capture request kalau jarak user
   ke spawn_point > radius yang diizinkan (dihitung ulang di backend pakai Haversine formula)
7. Terapkan CORS policy yang ketat, hanya izinkan origin dari app resmi
8. Semua endpoint yang menerima input harus di-sanitize dari SQL Injection (gunakan Eloquent
   query builder, jangan raw query tanpa binding)
9. Gunakan .env untuk semua secret (DB credential, APP_KEY), jangan hardcode
10. Tambahkan logging untuk aktivitas mencurigakan (misal: capture request dengan jarak GPS
    yang tidak masuk akal / teleport detection sederhana)

ENDPOINTS YANG DIBUTUHKAN:

Auth:
- POST /api/register
- POST /api/login
- POST /api/logout (auth)
- GET  /api/me (auth) — data profile user

Map & Location:
- GET  /api/game-locations — daftar area game valid (untuk cek "Apakah di Area Jatim Park/Baloga?")
- GET  /api/spawn-points/nearby?lat=..&lng=..&radius=.. — monster terdekat dari posisi user (auth)

Capture Flow (sesuai flowchart: cek jarak < 10m, swipe lempar bola, cek kena/meleset):
- POST /api/captures/attempt (auth) — body: spawn_point_id, lat, lng, item_id (bola yang dipakai)
  ? server validasi ulang jarak, hitung probabilitas kena berdasarkan rarity monster,
    kurangi item_id dari inventory, kalau berhasil insert ke captures + inventories

Species & Encyclopedia:
- GET  /api/species (auth) — daftar semua species dengan status "discovered" per user
- GET  /api/species/{id} (auth) — detail species

Inventory & Items:
- GET  /api/inventory (auth)
- GET  /api/items (auth)

Missions:
- GET  /api/missions (auth) — daftar misi + progress user
- POST /api/missions/{id}/claim (auth) — klaim reward misi selesai

Leaderboard:
- GET  /api/leaderboard — top user berdasarkan points (public, cache 5 menit)

Buatkan semua Controller, Form Request untuk validasi, API Resource untuk response,
dan daftarkan route-nya di routes/api.php dengan grouping middleware yang sesuai.
```

## PHASE 4 — Implementasi Flow Sesuai Flowchart

```
Implementasikan logic berikut di project Flutter "baloga_ar_rescue" PERSIS sesuai flow ini:

1. SPLASH & GPS CHECK
   - Saat app dibuka: cek permission GPS (pakai permission_handler)
   - Kalau GPS tidak aktif/tidak diizinkan ? tampilkan dialog "Aktifkan GPS Anda" dengan
     tombol buka Settings
   - Kalau GPS aktif ? ambil koordinat user (geolocator)

2. AREA VALIDATION
   - Kirim koordinat ke endpoint GET /api/game-locations, cek apakah user berada dalam
     radius salah satu game_location (hitung jarak Haversine di client untuk UX cepat,
     TAPI backend tetap re-validasi saat capture)
   - Kalau di luar area ? tampilkan pesan "Silakan datang ke Baloga" dan disable fitur capture
   - Kalau di dalam area ? lanjut ke Map Mode

3. MAP MODE (screens/map)
   - Tampilkan flutter_map dengan posisi user real-time (marker biru bergerak)
   - Fetch GET /api/spawn-points/nearby, tampilkan marker monster di peta
   - Hitung jarak user ke tiap monster setiap update lokasi (interval 3 detik, hemat baterai)
   - Kalau jarak < 10 meter ? marker monster jadi "tappable" (bisa disentuh), highlight visual
   - Kalau >= 10 meter ? marker tetap terlihat tapi tidak bisa disentuh (redup/disabled)

4. CAPTURE SCENE (screens/capture) — versi 2D pakai Flame
   - Saat marker monster di-tap (dan jarak valid): pindah ke CaptureScreen
   - Tampilkan sprite/gambar monster besar di tengah layar dengan animasi idle sederhana
     (bobbing up-down pakai Flame effect)
   - Tampilkan bola capture (Eko-Sphere) di bawah, bisa di-drag lalu swipe ke arah monster
   - Deteksi collision: kalau lintasan swipe mengenai bounding box monster ? "kena",
     kalau meleset ? animasi bola terpental / hilang
   - Kalau kena: hitung probabilitas berhasil di sisi CLIENT hanya untuk animasi
     (visual saja), keputusan FINAL tetap divalidasi ulang lewat POST /api/captures/attempt
   - Kalau server response sukses: tampilkan animasi "BERHASIL! [Nama Monster] telah
     diselamatkan" + card species baru (kalau memang baru pertama kali capture)
   - Kalau gagal (server tolak, misal item habis / jarak curang) ? tampilkan pesan error
     yang sesuai, jangan expose detail teknis ke user

5. KEMBALI KE MAP
   - Setelah capture (berhasil/gagal), kembali ke Map Mode, refresh daftar spawn points

Gunakan flutter_riverpod untuk manage state lokasi user, daftar monster nearby, dan
status capture supaya semua screen sinkron.
```

## PHASE 6 — Security Hardening untuk Publish ke Play Store

```
Terapkan security checklist berikut di project Flutter "baloga_ar_rescue" DAN backend
Laravel "baloga-api" sebelum publish ke Play Store:

FLUTTER SIDE:
1. Aktifkan code obfuscation saat build:
   flutter build appbundle --obfuscate --split-debug-info=build/debug-info
2. Simpan base URL API dan semua key sensitif di file .env (pakai flutter_dotenv),
   tambahkan .env ke .gitignore, JANGAN commit ke repository
3. Ganti flutter_secure_storage untuk semua data auth token (bukan shared_preferences)
4. Aktifkan SSL Pinning di dio client (certificate pinning) supaya traffic API tidak bisa
   di-intercept lewat MITM proxy (misal saat testing dengan Charles Proxy/Burp Suite)
5. Set requestLegacyExternalStorage: false dan review semua permission di AndroidManifest.xml
   — hanya minta permission yang benar-benar dipakai (ACCESS_FINE_LOCATION, CAMERA jika perlu)
6. Nonaktifkan debug logging di build release (hapus semua print()/debugPrint() sensitif,
   atau bungkus dengan kIsWeb == false && kDebugMode check)
7. Cegah screenshot di screen sensitif kalau perlu (opsional, pakai package no_screenshot)
8. Tambahkan Root/Jailbreak detection sederhana (package: flutter_jailbreak_detection) untuk
   mencegah cheat GPS spoofing yang sering dipakai di perangkat root

BACKEND LARAVEL SIDE:
1. Set APP_DEBUG=false di .env production (WAJIB, kalau true bisa expose stack trace ke publik)
2. Set APP_ENV=production
3. Paksa HTTPS: tambahkan middleware force HTTPS di production, gunakan Let's Encrypt SSL
4. Set CORS hanya izinkan domain/app resmi (bukan wildcard *)
5. Aktifkan Laravel rate limiting yang sudah dibuat di PHASE 2
6. Set session/token expiry yang wajar (misal token Sanctum expired dalam 30 hari,
   refresh mechanism kalau perlu)
7. Backup database otomatis terjadwal (kalau hosting support, misal Railway/DO snapshot)
8. Pastikan semua endpoint capture melakukan re-validasi jarak GPS di server (anti-cheat)
9. Tambahkan Laravel Telescope HANYA di environment local/staging, JANGAN aktif di production
   (bisa expose data sensitif kalau kebobolan)

PLAY STORE COMPLIANCE:
1. Siapkan Privacy Policy (wajib karena app pakai lokasi & kamera) — jelaskan data apa
   yang dikumpulkan (lokasi, akun) dan untuk apa
2. Isi Data Safety form di Play Console sesuai data yang benar-benar dikumpulkan
3. Minta permission lokasi dengan penjelasan jelas ke user (runtime permission rationale)
4. Test app di berbagai device dengan Android App Bundle (.aab), bukan APK biasa untuk submit
```
